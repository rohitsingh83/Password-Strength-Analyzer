10 password security rules

Each rule includes the reason it exists — because “best practice” without a reason does not change behaviour.

Entropy: useful, but easy to misread

Entropy estimates how uncertain an attacker is about the value, in bits. The classic estimate is:

Entropy ≈ length × log2(pool size)

That formula assumes every character was chosen uniformly at random. Humans do not do that: they take a memorable word and add a year or a symbol. So the formula is an upper bound for human-chosen passwords.

  • Theoretical bits — the optimistic number from the formula.
  • Effective bits — theoretical minus a penalty for every predictable structure found.
  • Shannon bits — a variety indicator from the character distribution (it cannot see dictionary words).
⚠️Treat any “time to crack” as an illustration, not a fact. Real resistance depends on the attacker model (online vs offline), the hashing algorithm and work factor, rate limiting and lockout, and whether the hash database has already leaked.

Password vs passphrase

A passphrase is several randomly chosen, unrelated words. It is usually longer than a short random string and easier to memorise, which is why it can be a good trade-off.

bits ≈ words × log2(word-list size) — with a 6,000+ word list that is about 12.6 bits per word: 4 words ≈ 50 bits, 6 words ≈ 76 bits.

🚫Length alone is not enough. The famous “correct-horse-battery-staple” example is in every cracking wordlist — this analyzer flags it as a famous predictable phrase and caps it in the VERY WEAK band. Try it above.
✅Better: your own unrelated words, chosen randomly (or generated by a manager), used for exactly one account.

How production systems actually store passwords

A separate teaching demonstration with a synthetic value — never connected to what you type in the analyzer.

Password→ + unique random salt→ password hashing function (KDF)→ stored hash + parameters→ login: re-hash & compare
  • Hashing is one-way. Encryption is reversible with a key; hashing is not reversible at all. They solve different problems.
  • Salt per user. Identical passwords then produce different stored values, so one precomputed table cannot crack many accounts at once.
  • Slow by design. Argon2id, scrypt, bcrypt and PBKDF2 are deliberately expensive and tunable. General-purpose fast hashes (MD5/SHA-1/SHA-256 alone) help the attacker.
  • Never store plaintext. A plaintext store turns any read-only database leak into an instant account takeover for every user.

Real-world login security: password strength is one layer

Password+ MFA+ Rate limiting+ Secure password hashing+ Lockout / abuse protection+ Session security+ Phishing protection+ Monitoring

A perfect password cannot save an account whose login page is a phishing clone, whose sessions never expire, or whose password database was stored with unsalted MD5. Conversely, MFA keeps an account safe even when a strong password leaks — which is why both belong in the answer.

Limitations & future improvements

Honest boundaries of this build — the part interviewers actually probe.

Limitations

  • The 0–100 rubric and the classification bands are project-defined, not a universal security standard.
  • The dictionary and keyboard lists are deliberately small and educational; a real deployment would use a licensed corpus (for example a properly attributed 10k+ list).
  • Entropy is an estimate. A single formula cannot determine strength.
  • The demo breach corpus is tiny and local. Production would use a k-anonymity range API, sending only the first 5 hash characters.
  • Strength does not model reuse, phishing, malware or session theft — the surrounding controls matter.

Future improvements

  • Swap in a peer-reviewed estimator (zxcvbn-style) and compare results side by side.
  • Configurable enterprise policies with audit export and IAM integration concepts.
  • Privacy-preserving breached-password lookup using k-anonymity and range queries.
  • WebAuthn/passkey and passwordless education flows; MFA adoption nudges.
  • Localisation, accessibility review with screen readers, and organisation-level aggregate reporting that still never collects passwords.
  • A browser-extension mode that scores locally on signup forms.

Threat model for this tool

What it defends against, and what it does not.

In scope

  • Weak, common, patterned, reused-in-spirit and context-derived passwords.
  • Misleading composition-only meters that reward predictable strings.
  • Practices that turn an analytics feature into a credential leak.

Out of scope (and explicitly not implemented)

  • No cracking, no credential stuffing, no authentication bypass, no guessing against any account.
  • No collection of real user passwords, and no storage of anything derived from them.
  • No claim that a high score means an account is safe.
